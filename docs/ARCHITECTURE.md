# PQTABS architecture (production)

This document replaces the single-operator model in `IMPLEMENTATION-PLAN.md`. Chain facts in that plan remain the source for addresses and the precompile, re-checked on 2026-10-06: chain 5042, USDC `decimals() = 6`, Barkeep factory `0xccebc58dd1f5937b36d5f9f89f0754424f4d443c` code size 2355, implementation `0x89B63f2E43dea9014750925C01996D34856B01D2`.

## What changed, and why

| Old assumption | Production decision | Why |
|---|---|---|
| One PQ key for the whole system | One PQ key per user root | A shared seed is a shared treasury. User A’s compromise would be User B’s compromise. |
| One demo agent key | One ECDSA agent key per tab | Barkeep writes the agent into immutable clone args. A tab cannot rotate its agent. A new capability is a new key and a new tab. |
| Operator CLI is the only signer | Each user signs their own root actions. The CLI is the expert and recovery tool. `signer/wasm` exports the same crate for a browser. | The server must not be able to forge a root action (I14, I24). |
| `maxOpenExposure` fixed forever | The user’s PQ key may set it, but never below the sum of open caps | A stolen PQ key can already `TRANSFER` the treasury. The ceiling exists to bound **agents**. The user must be able to lower it. |
| “Lost seed, funds stuck” as the only story | Passphrase-encrypted backup file the user holds. No admin recovery. | An ECDSA or operator backdoor would cancel the PQ claim. |
| Backend may later hold the agent key | Backend never stores agent keys or PQ seeds | One server secret that unwraps every agent is a cross-user breach. |

## Identity

A user is the wallet that calls `RootFactory.createRoot`. That wallet is stored as `registrar` and can do nothing else. It is how the product answers “which roots belong to this wallet?”

Authority over a root is the SLH-DSA-SHA2-128s verifying key stored in that root. The registrar cannot open tabs, move USDC, or rotate the key.

```
wallet (registrar, discovery only)
    └── PQRoot (own pqVk, own nonce, own exposure, own USDC)
            └── Barkeep tab (owner = this root, agent = its own ECDSA address)
```

User B’s signature includes B’s root address. It fails on A’s root (I18). A’s agent is not the agent on B’s tab (I12). A’s `openExposure` is storage inside A’s root (I21).

## Contracts

`RootFactory` has no owner and no upgrade. Its constructor deploys the `PQRoot` implementation and locks that implementation so `initialize` cannot be called on it. Users get EIP-1167 clones. The clone salt is `keccak256(abi.encode(msg.sender, userSalt))`, so a third party cannot occupy another wallet’s salt.

`PQRoot` pins USDC, the PQ precompile, and the Barkeep factory. `initialize` checks the Barkeep factory’s `IMPLEMENTATION()` and `USDC()` once. There is no proxy.

Digest domain is `keccak256("PQTABS_V2")`. Version 2 is deliberate: the action set includes `SET_EXPOSURE`, and each user has a distinct root address inside the digest.

Protected actions, each bound to nonce, deadline (at most 7 days), chain id, and this root:

1. `OPEN_TAB`
2. `CLOSE_TAB`
3. `TRANSFER`
4. `ROTATE_KEY`
5. `SET_EXPOSURE`

`reclaim` and `retrySweep` are permissionless and cannot choose a recipient. `reclaim` pays the root only after expiry, and only by calling Barkeep `close()`.

## Exposure

`openExposure` equals the sum of `cap` on tabs this root currently marks open.

Opening adds that cap or reverts. Spending does not change it. Closing or reclaiming subtracts it once. A failed USDC sweep sets `needsSweep` and does not subtract again. `retrySweep` does not touch exposure. Donations to a tab or to the root do not change exposure. Direct donations to a tab remain spendable by that tab’s agent; that is Barkeep, and the root never sends extra USDC to a tab.

## Agent custody

The agent key is generated by the user. The hosted backend accepts an already-signed USDC `transferWithAuthorization` and submits it. It cannot sign one. Root signatures are produced by `pqtabs-sign` or by `signer/wasm`, which calls the same `sign_digest` function.

Compromise of an agent key spends that tab only: allowlisted payees, `maxPerCall`, remaining balance, until expiry or PQ-signed close.

Revocation is `CLOSE_TAB`. Rotation is a new key, a new tab, and close of the old one, because Barkeep terms are immutable.

## PQ backup

`pqtabs-sign backup` writes a file encrypted with Argon2id and AES-256-GCM under a passphrase the server never sees. `restore` decrypts that file onto a path the user chooses and prints the verifying key. The user compares that key with `pqVk()` on their own root. The server never receives the passphrase or the decrypted file. Losing both the device and the backup leaves that root’s USDC unmovable. There is no operator override.

## Backend

Stateless. Chain is authoritative. No database: roots and tabs are factory and root events plus view calls. Rate limits and idempotent relay are process memory; a Render restart drops them and the chain still enforces nonces. Documented as a free-tier constraint, not a second ledger.

## Deployment sequence

Staging and production share bytecode. The first mainnet factory is exercised with disposable PQ keys and tiny USDC. If that gate fails, that address is abandoned and a new factory is deployed. If it passes, the same factory is the production factory, because it has no admin to “promote” and redeploying would split users across two bytecodes. Production users then create their own roots. The disposable staging roots are not reused for real balances.
